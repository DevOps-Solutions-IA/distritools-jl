## Findings and corrections

- Admin payment-event detail was not scoped tightly enough to the gateway reference; event reads are now scoped by gateway and `payload.gatewayReference`, bounded to 50, and serialize safe scalar values.
- Order details could expose address/notes/name to ordinary order readers. Sensitive fields now require `customers.read_sensitive`, and the access is audited. Financial values are independently gated by `reports.financial.read`.
- Customer and payment outputs had excessive relation selection; queries now select only required fields. Customer list GET no longer upserts profiles from recent orders, avoiding an unaudited write on a read. The customer registry represents persisted Customer records; checkout-only guest buyers remain available through Orders. Existing guest-to-customer materialization remains in explicit quote/shipment flows.
- Shipment/notification DTOs could include provider/internal snapshots or message details. Responses now use allowlists and masks; shipment event rows no longer return raw descriptions.
- Historical audit JSON redaction did not cover all PII-like field names. Sanitization now masks identity/contact/address/document/recipient fields on historical read as well as writes, along with existing secret/token protections.
- Report/dashboard source caps did not bound nested relations or aggregate materialization. In a single PostgreSQL `REPEATABLE READ` read transaction, count preflight totals relevant root and relation rows and rejects above 50,000 before loading report DTOs; deterministic `take + 1` child caps are secondary safeguards. The shared snapshot closes the count/materialization race; overflow never returns partial totals.
- Report query filters now reject malformed/unsupported ranges and enum-like filters before DB access. Sensitive amounts are permission-gated at both controller/use-case boundaries.
- Spreadsheet formula payloads are neutralized after leading whitespace/control characters, while legitimate numeric negative values remain numeric.
- Report export audit persistence failure prevents export data from being returned.
- Permission denial logs no longer include actor email or user identifier.
- Customer export remains disabled; `includePii` export remains forbidden. No bulk extraction path was added.

## Export / PII invariants

- No raw JWT/session/refresh token, password, 2FA secret, encryption key, authorization header, cookie, provider credential or webhook raw body is added to an admin response, export or audit DTO.
- Report queries select only reporting fields; customer contact/address data is not selected for reports.
- Customer PII is masked by default. Explicit reveal is guarded and audited.
- Financial reports and values require `reports.financial.read`; sensitive payment detail requires both `payments.read` and the financial permission.
- Customer PII export is not implemented and remains blocked by contract.
- CSV values are escaped for quoting and formula-leading `=`, `+`, `-`, `@` including obfuscated leading whitespace/control characters. Numeric negative values are preserved.
- PDF is existing export behavior; report output is bounded and uses safe DTO rows and masked actor metadata.

## User impact and rollback

Ordinary admins see masked customer identity/address/notes and protected financial fields. Sensitive reads require existing granular grants and leave audit evidence. Invalid or overlarge report filters/relations fail closed; operators must narrow filters rather than receive partial results. Customer profile listing is now read-only; order-only guest purchasers remain accessible in order operations but are not silently materialized by a customer-list GET. No schema change exists; rollback is application-only and no data conversion is required.
