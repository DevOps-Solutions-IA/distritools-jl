## State, retry and recovery behavior

- The inbox transaction captures notification intent and `notification.queued` audit intent atomically. A failure creating either persistence write rolls back the notification and inbox completion; recovery is not invoked on transaction failure.
- PostgreSQL notification rows remain the recovery source. Redis queue jobs use the original notification UUID as `jobId`; recovery can reconstruct a missing job without changing event identity or logical intent.
- A shared maximum of three *business delivery claims* now constrains PostgreSQL recovery selection, `claimForSend`, and BullMQ `attempts`. Rows at the cap remain `failed` and operator-visible but are not automatically re-enqueued. This is not exactly-once delivery.
- Recovery claims use `FOR UPDATE SKIP LOCKED` and a lease/fencing token. Concurrent workers acquire one row at most once; claim release accepts queued/failed state so a retryable failed row remains recoverable after a Redis enqueue failure.
- If BullMQ still retains the same notification job ID as `failed`, recovery validates the job name and embedded notification ID and reactivates that job rather than treating duplicate `queue.add` as successful dispatch. If a retained `completed` job conflicts with still-eligible PostgreSQL state, it is removed and reconstructed under the same ID. DB state and attempt cap remain authoritative; workers in waiting/active/delayed states are not duplicated. Enqueue/remove/retry failures release the fenced DB claim and leave the row recoverable.
- An expired `sending` claim becomes `uncertain`, not automatically resent. A legacy expired row with a null claim token now receives a deterministic safe audit-intent transition key (`expired:<notificationId>`) instead of aborting the recovery transaction.
- Successful, failed, and uncertain transitions preserve existing transactional audit intent and token fencing. Sent/uncertain are not blindly replayed.
- No post-exhaustion operator retry/replay endpoint exists in the current notification controller (only authenticated, permissioned, paginated read). No endpoint or policy was added: replay authorization and handling of uncertain outcomes require a separately owned operational decision. Existing replay routes remain disabled/guarded.
- Application shutdown remains bounded by existing recovery/worker shutdown behavior; interruption leaves persisted queued/sending intent subject to lease recovery, rather than recording a provider success.

## Implemented changes

- `PrismaNotificationRepository` enforces the common 3-attempt bound when selecting queued/retryable failed work and claiming provider attempts. It recovers legacy expired sending rows without a claim token and releases enqueue claims for failed rows as well as queued rows.
- `NotificationDispatchRecoveryService` uses the same attempt constant for BullMQ job options, avoiding drift between queue retries and durable DB eligibility.
- Mock email and WhatsApp providers now fail closed with safe `PROVIDER_BLOCKED` in production/staging (including conflicting environment markers). This prevents synthetic/mock success from being persisted as delivered and prevents the local email provider from writing customer content to disk in production/staging. Local/test mock behavior remains available for tests only.
