## Scope and cause

No P1/P2 candidate finding was established by executor testing; independent challenger review remains outside this executor's PASS claim.

Only the authorized existing `src/infra/queue/redis-role-connection-options.ts` and `src/infra/queue/bullmq.module.ts`, new `src/infra/queue/role-aware-worker.ts`, new unit/critical EX-08 queue lifecycle tests, and this report are changed. Existing tests, helpers, bounded-worker-shutdown, CI, dependencies and schema are unchanged. Integrity evidence verifies 134 existing files against HEAD byte for byte.

The installed Nest BullMQ explorer selects the registered queue options before consulting a processor's shared configKey. Consequently both real processors inherited producer offlineQueue=false/retryLimit=1/no reconnect even though their decorators selected the persistent worker configuration. Queue readiness also does not settle either worker initialization. Closing the application immediately after queue readiness can close those connections while the Redis INFO handshake is pending and cause a late SDK unhandled rejection.

The owned, real Redis minimal Nest baseline reproduced the exact Stream-not-writeable rejection in thirty create/close cycles (FAIL, exit 1, 32.007s). A same-source control that awaited both workers before app.close passed thirty cycles (PASS, exit 0, 1.722s). Changing only worker role flags while retaining premature close still failed (FAIL, exit 1, 30.889s, Connection is closed). These distinguish the configuration mismatch from the lifecycle ordering defect; flags alone are insufficient. A no-network selector probe independently showed both processors received the producer flags (FAIL, 0/2 assertions). Root reproduced the causal baseline and readiness-only control independently on its own services; root evidence is separately owned and is not counted as executor gates here.

Initial external diagnostics accidentally resolved ancestor node_modules rather than this worktree's packages and produced harness failures. Those logs are preserved and excluded from product conclusions; corrected diagnostics explicitly resolve owned packages. Negative fixture revisions likewise preserve their FAIL evidence: events.once(ready) rejected on an expected connection reset, and a disconnected producer's final QUIT can succeed or fail depending on teardown timing. The final fixture asserts enqueue rejection and validates any specific teardown error; it does not suppress unhandled rejections or weaken existing tests.

## Behavior and impact

It preserves host, port, database, authentication and TLS without reading environment variables during import. Producer construction and its fail-fast policy are unchanged. SDK close waits for both command and blocking initialization through Worker.waitUntilReady. Initialization waiting has a 5s graceful deadline or 250ms forced deadline; an initialization error/deadline forces SDK cleanup and propagates the failure. Existing shutdown budgets (150s graceful and 2s forced) and shutdown helper are unchanged. Active processing/replay/audit policies are outside this change.

The real Nest fixture overrides only public queue option providers with an exclusive random prefix on the verified disposable Redis target. It asserts all three producer prefixes before app.init and both real worker prefixes afterward. Fake business dependencies permit no provider/job operation. Outage tests use local ephemeral TCP proxies and unavailable local ports; they neither stop Redis nor affect another broker.

User impact proposed for the orchestrator's USER_IMPACT_LOG: application shutdown no longer races worker initialization under repeated auth test application creation. Workers retain persistent Redis reconnect behavior; producers still reject unavailable Redis without buffering. Connection identity, TLS and durable business retry/replay policy remain governed by the existing injected configuration and contracts. This does not certify a functional endpoint, real email/WhatsApp/shipping/payment provider, cutover, or production readiness.
