## Objective
Remove direct `PrismaService` transaction ownership from `ProcessPaymentWebhookUseCase` by introducing a narrow application-facing payment-webhook unit-of-work/transaction runner implemented by a Prisma infrastructure adapter.

This is a behavior-preserving architecture seam. Do not redesign payments, inventory, webhook idempotency, audit, events, providers, or APIs.

## Invariants that must remain unchanged
1. Invalid webhook signature fails before receipt/state mutation.
2. `(gateway, externalEventId)` is claimed atomically; concurrent duplicates produce one applied delivery and idempotent duplicates.
3. Receipt claim/processed state, payment transition, order transition, order-item read and inventory commit/release remain inside one transaction.
4. Any transactional failure rolls all those DB effects back.
5. Approved commits reserved stock once and transitions payment/order exactly as today.
6. Rejected/expired releases reserved stock once and preserves current terminal states.
7. Preserve current Prisma transaction options, including maxWait/timeout.
8. Audit and domain-event publication remain post-commit; do not solve EX-04/outbox concerns here.
9. No real payment provider call; tests use current mock/test provider semantics.

## Allowed implementation
- Add a narrow application port/token such as `PAYMENT_WEBHOOK_UNIT_OF_WORK`.
- Add a Prisma infrastructure adapter that owns `$transaction`.
- Bind it in the appropriate module.
- Change `ProcessPaymentWebhookUseCase` to inject/use the port instead of `PrismaService`.
- Add focused unit tests for one delegation, one transaction context, result propagation, error propagation and preservation of configured transaction options.
- Reuse existing repository transaction context types if needed to keep this seam bounded; broader Prisma type cleanup is deferred.

## Hard stops
- No Prisma schema or migration.
- No payment/order/inventory state-rule changes.
- No retry-policy changes.
- No webhook receipt/idempotency-key redesign.
- No API/DTO response change.
- No provider credential or external-provider call.
- No event transport/outbox changes.
- No broad relocation of shared transaction-client types.
- No weakening/skipping replay, cancellation-race, stress, or signature tests.
- Stop if preserving atomicity requires any of the above.
