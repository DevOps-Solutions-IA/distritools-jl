## Orchestrator-selected operational policy

### Connections and outage behavior

Use the installed BullMQ 5.81.5 / @nestjs/bullmq 11.0.4 / ioredis 5.11.1 contracts; confirm the lockfile before implementation. Do not copy newer major-version APIs from current documentation.

Producer enqueue calls must have a finite failure path: producer-specific `enableOfflineQueue: false`, `maxRetriesPerRequest: 1`, and an explicit connection/operation deadline with a starting connection budget of 5 seconds. A caller timeout alone is not cancellation: an enqueue with an unknown result remains retryable using the same stable job ID, and must not be reported as a definitive rejection or completed delivery.

Workers use their own persistent connections with `maxRetriesPerRequest: null`, error observation and reconnect behavior appropriate to BullMQ. Do not reuse a fail-fast producer connection as a blocking worker connection.

Test Redis already unavailable before application startup as well as loss after readiness. No endpoint/process may wait indefinitely merely because no connection was ever established. HTTP liveness reports process health independently; readiness reflects the capabilities needed by that role. Security/auth dependencies continue to fail closed.

A global Redis outage pauses or backs off new relay claims; it must not consume every event's business-attempt budget and park the entire backlog. Intent remains in PostgreSQL. Distinguish outage/circuit delay from a consumer attempt that actually ran. Resume gradually with bounded batch size/concurrency, without a reconnect stampede.

Queue Redis must have an explicit persistence and no-eviction deployment requirement. Do not silently alter a Redis instance shared with security/cache workloads. Configuration evidence and queue durability limitations belong in the final operational checklist.

### Retry classification and durable parking

| Failure class | Policy |
| --- | --- |
| Transient consumer/database failure | Initial policy: 5 total delivery attempts, exponential backoff starting at 2 seconds, 50% jitter, capped at 60 seconds; verify behavior against pinned BullMQ |
| Definitive notification not-sent result | Preserve the existing 3-attempt business limit, with bounded backoff |
| Unknown provider result or expired sending lease | Persist `uncertain`; no automatic resend or claim of success |
| Invalid envelope, unsupported version or missing required consumer | Terminal, observable failure/parking; never successful discard or empty handler |
| Redis unavailable before/around enqueue | Retain durable intent and stable ID; outage recovery policy, not a fabricated successful delivery |
| Inbox envelope identity conflict | Fail closed, retain identity/evidence and surface an actionable safe category |

Persist parking in PostgreSQL with the original event/delivery identity, required consumer/disposition, bounded safe error category, attempt evidence, timestamps and replay audit identity. Do not persist arbitrary provider responses, stack dumps, recipient payloads, credentials or tokens in parking summaries.

A BullMQ failed-event callback is only one signal. Implement bounded reconciliation so a crash between exhausted queue execution and parking cannot permanently lose the failure record. Repeated signals/reconciliation must be idempotent.

Retain failed queue evidence until durable parking is confirmed. Queue retention is an operational diagnostic policy, not the deduplication ledger. Start with completed-job diagnostics bounded by both 7 days and 10,000 jobs; document that either limit may remove earlier data and correctness must survive removal. Keep queue identity stable across retries/removal/reconstruction.

Manual replay must be bounded, dry-run inspectable, authorized through the existing operational mechanism, audited and based on a concrete safe disposition. Replay the original event/consumer identity through the same inbox. A replay of sent/uncertain notifications follows their durable guard; it must not reset their state, clear receipts or create new IDs to force execution. Do not build a new replay UI in this phase.

### Complete consumer eligibility and Redis data loss

The current registry's presence of any handler is insufficient for production eligibility. Compare the required independent consumer set in the existing contracts/discovery with real registered effects and durable receipt identities. Every required consumer must have a safe disposition before an event can be eligible; unresolved consumers stay explicit.

Reconcile eligible durable records whose enqueue was acknowledged but whose Redis job subsequently disappeared. Use PostgreSQL intent and per-required-consumer completion to decide whether work remains. Missing queue/job/inbox evidence alone cannot prove historical absence of side effects. Tests must cover retained jobs, removed jobs and complete loss of the isolated queue's data.

Historical held events are a separate class from operational parking. Neither a new DLQ table, startup, reconnect, readiness flag nor replay command may promote or modify them. A later cutover requires read-only history classification, a concrete disposition for every required consumer, and a persisted per-event routing boundary. A process clock or automatic fallback to legacy is not such a boundary.

### Graceful shutdown

Stop timers and new outbox/recovery claims before closing connections. Drain workers with an explicit deadline; BullMQ worker close alone has no inherent timeout. Start with a 150-second role shutdown budget, aligned with the current 120-second notification send lease; tests use reduced deterministic durations.

On deadline/kill, preserve PostgreSQL intent, inbox progress and fenced claims. Recovery may continue safe database work but must not blindly resend an ambiguous external call. A stale worker must not finalize a newer claim after restart. Do not shorten leases or fake completion to make shutdown tests pass.

## Acceptance tests

1. Redis unavailable before bootstrap: producer operations fail within the documented bound; role readiness is false/limited as specified, process diagnostics remain available, and security behavior stays closed.
2. Runtime Redis outage during enqueue, unknown enqueue result, reconnect and retry preserve the same identity and pending durable intent; no false delivered/completed state.
3. Global outage does not exhaust/park untouched backlog; multiple relays recover with bounded claims/backoff and no starvation.
4. Transient consumer failures exercise the exact attempt/backoff boundary; terminal invalid/unsupported/missing-consumer cases create durable evidence without successful no-op handling.
5. Worker crash between final failure and parking signal is repaired by bounded reconciliation. Duplicate failed signals/flushers/restarts yield one logical parking/audit record.
6. Replay with retained jobs, removed jobs and lost queue data executes only safely incomplete required work. Completed consumer receipts suppress duplicate DB effects; notification sent/uncertain guards survive job loss.
7. Eligibility checks reject incomplete consumer coverage even if another consumer is registered. No tests add dummy handlers to make that condition pass.
8. Multi-batch search with more than one worker/delivery preserves atomic progress, lock ordering, fairness and truthful completion; current public reindex API semantics remain intact.
9. Owned-process SIGTERM and forced termination preserve intent and recoverability at pre-effect, mid-batch and post-commit boundaries. Stale claims cannot finalize newer work.
10. Historical held fixtures remain byte-for-byte unchanged across startup, outage recovery, parking reconciliation, flags and replay dry runs.
11. Notification audit outage/recovery remains independent of provider resend. Original audit transition times and one logical audit per transition survive failures.
12. Existing order/payment/webhook replay, permissions, API serialization, catalog/search and notification regressions remain green; no new real-provider call or readiness bypass.
13. Logs/status/parking/replay evidence include safe identifiers and error categories, never PII payloads or secrets.
14. Any additive schema has forward/preserve-data rollback guidance and a forward/test-only reverse/forward gate on a newly created guarded database. A test reverse refuses populated durable history.

Use barriers/fault injection with deadlines, not sleeps or retry-until-pass. Stop each owned disposable service/process through its recorded identity; never kill shared developer or production services.
