### Endpoint and token semantics

| Endpoint | Authentication | Throttle / permission | Purpose |
|---|---|---|---|
| `POST /api/v1/auth/login` | Public | `auth`: 5/min | Password verification; returns a one-use 2FA challenge only. |
| `POST /api/v1/auth/verify-2fa` | Public challenge flow | `auth`: 5/min | Verifies TOTP, consumes challenge, then creates persisted session and access/refresh pair. |
| `POST /api/v1/auth/refresh` | Public refresh credential | `default`: 10/min | Validates persisted session/hash/current JTI and rotates refresh state atomically via CAS. |
| `POST /api/v1/auth/logout` | Bearer access token | JWT guard | Revokes current persisted session. |
| Admin operations | Bearer access token | Global JWT then route permission | Authenticated without permission is 403; unauthenticated is 401. |
| `GET /api/v1/admin/domain-events/cutover-readiness` | Bearer access token | `domain_events.cutover.read` | Read-only, bounded operational evaluator; EX-04 cutover remains deferred. |

Tokens use separate secrets, audiences and intended purposes. Effective maximum/defaults are 15m access, 7d refresh and 10m challenge; positive shorter durations are allowed. Refresh `168h` normalizes to the same exact maximum as `7d`. A single strict parser converts approved units to milliseconds; startup/readiness and token issuance share it, and JWT `expiresIn` receives normalized numeric seconds. Unsupported, malformed, ambiguous, zero, negative, overflow, nonrepresentable and production/staging over-limit values fail without fallback. Access requests are bound to a persisted session. Refresh values are stored as bcrypt hashes. No exactly-once or provider-delivery claim is made.

## Fixes and schema

- Environment classification checks both environment variables; recognizes `prod`, `production`, `staging` independent of conflicting labels.
- Dev-admin bypass remains available only for the existing explicit local/test configuration and cannot activate under production-like labels.
- Production auth startup/readiness validates required secrets, >=32-character high-diversity signing and 2FA encryption keys, auth-enabled state and TTL syntax/range/maxima. CORS empty/wildcard configuration is rejected in production/staging.
- Unknown, inactive and 2FA-ineligible login responses are normalized to `Invalid credentials`; existing account state behavior and password policy are unchanged.
- Refresh rotation uses a conditional update matching session, expected current JTI, not-revoked/not-compromised state and unexpired session. CAS loser fails closed and revokes the token family.
- 2FA challenge JTI is persisted and conditionally consumed once before session creation.
- Audit sanitizer recursively redacts sensitive key names, including punctuation/case variants.
- Additive Prisma model/table: `AuthTwoFactorChallenge` / `auth_two_factor_challenges`, keyed by challenge UUID, with user, expiry, consumed timestamp, creation timestamp and lookup index. No FK or existing session/audit/outbox record was changed or deleted.
- Migration deploy succeeded on a new disposable DB. Direct migration forward -> guarded `rollback.test-only.sql` reverse -> forward succeeded on database `ex051_migration_test`; the reverse refuses any database other than that exact test DB and refuses rows. Production rollback must retain the additive table and records.
- Deploy the additive migration before the new application. Challenges issued by an older binary have no persisted row and must be reissued after rollout. Rolling an old binary back would restore replayable, unpersisted challenges; it is not certified security-compatible. Rollback requires a controlled challenge invalidation/secret-rotation plan or, preferably, forward fix.

## Challenger

- Independent challenger identified P1: conflicting `APP_ENV=local`, `NODE_ENV=prod` could activate dev-admin bypass; fixed by normalizing both labels and adding regression coverage.
- Independent challenger found P2: short signing secrets and a predictable 2FA encryption key could pass readiness; fixed with length/diversity checks and regression tests.
- Final independent review found the encryption key check must cover the exact AES material, not an entropy-rich suffix. ## User impact, debt and boundaries

- Login now intentionally returns the same generic credential failure for unknown, inactive and 2FA-ineligible accounts. Clients must not depend on the prior 2FA-configuration-specific message.
- One-use 2FA challenge rows are now persisted; a challenge can only establish one session. An in-flight challenge minted before deployment will be rejected by the new verifier and the user must restart login.
- Production/staging startup now fails for missing/short/placeholder auth secrets, enabled dev bypass, malformed explicit token lifetimes, missing/short 2FA encryption key, empty CORS origins or wildcard CORS. Readiness reports non-ready for invalid auth security configuration.
- No password policy, lockout threshold, valid token lifetime, business permission/role, provider, HTTP enrollment/recovery surface or real notification was added or changed.
- Existing plaintext 2FA seeds will be rejected in production/staging; controlled migration/re-enrollment planning is a release prerequisite if such records exist.
- Current throttling uses process-local memory, so replicas do not share an aggregate limit. Trusted proxy is intentionally not enabled without deployment topology/allowlist decision.
- Security obligations remain open: `SEC-PRISMA-HIGH-001`, `SEC-SWAGGER-MOD-001`, `SEC-FRONTEND-TOOLING-HIGH-001`, `GOV-BRANCH-PROTECTION-001`.
- Real email/SMS/WhatsApp/payment/shipping providers remain `BLOCKED_PROVIDER`. EX-04 remains cutover-deferred; `order.paid` notification gap remains EX-07-owned; `inventory.low_stock_detected` producer gap remains EX-06-owned. Historical held/cutover-pending state was not changed.
