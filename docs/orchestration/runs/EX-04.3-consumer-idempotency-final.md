## Problem and resulting behavior

Repeated or concurrent legacy/future durable delivery previously lacked a shared durable consumer receipt. A committed Notification row could be stranded when the subsequent BullMQ enqueue failed. Search upserts lacked transaction-scoped serialization against overlapping projection work.

`DomainEventInbox(consumerKey,eventId)` now provides the durable uniqueness boundary for `notifications.v1` and `search-projection.v1`. Canonical SHA-256 envelope comparison rejects conflicting reuse of an identity. Transaction-scoped advisory locks serialize the same consumer/event; different consumer keys remain independent.

Notification rows and their initial audit intent commit with the inbox receipt and completion. Replayed delivery cannot create another logical notification or queued audit. Recovery independently discovers explicitly eligible notification rows, claims a bounded set, enqueues outside the DB transaction using the persisted notification ID as jobId, and releases only its own claim. A completed inbox does not suppress pending dispatch recovery.

Workers recheck persisted state, take a fenced `sending` claim and call providers outside every DB transaction. Only a valid unexpired claim can finalize its transition. Definitive not-sent errors preserve retryable `failed` behavior; an unknown provider outcome or expired send lease becomes `uncertain`, without blind resend. Persisted `sent` remains a guard after the BullMQ job is removed. These mechanisms do not claim exactly-once external delivery.

Notification state transitions and their `NotificationAuditIntent` records commit atomically. Flush uses the intent UUID as audit identity, preserves the original transition time, and commits audit insertion plus consumption together under bounded SKIP LOCKED selection. Failed audit flush remains recoverable and does not consume provider-send attempts or cause a second send. Stale claim owners cannot create audits for transitions they did not commit. `notification.queued` now means durable scheduling intent, explicitly distinguished from queue acceptance and delivery.

Search processes at most 50 source IDs/locks per transaction and at most 100 batches per durable delivery. The inbox persists the initial upper bound and last committed cursor. Each batch commits its projection and cursor together; a failed batch rolls back both while earlier committed batches survive. Completion is recorded only after the final batch; budget exhaustion remains retryable. Source locks are sorted and source rows are reread after acquiring them. This is a bounded current-source projection, not an immutable catalog snapshot; new IDs behind an already committed cursor depend on their own supported lifecycle event.

Public manual reindex requests preserve their existing semantics: absent IDs and `ids: []` both request full reindex. Internal `execute([], tx)` remains an empty batch. Manual calls use bounded transactions without inventing domain events.

## API and operator impact

Classification: **NOTIFICATION**, including the disclosed admin delivery-state extension.

Existing successful checkout/order/payment response payloads, business state rules, event names/versions/payloads, templates and recipients remain unchanged. The failure boundary changes for supported committed notification intent: a Redis enqueue error caught by recovery leaves eligible pending work, and an audit-flush error leaves durable audit intent, instead of requiring the originating business operation to fail solely for that post-commit step. This is pending work, not a claim of queue acceptance or delivery. Database/inbox failures and unsupported handlers remain observable failures.

The admin notification API may return `sending` and `uncertain`. Operators must not treat sending as delivered or uncertain as safe for retry. Repository serialization explicitly lists public fields; claim tokens, leases, eligibility and internal error codes are excluded. Existing authentication, `notifications.read` permission and payload masking remain in force. The frontend already treats status as a string and renders these states through its existing warning branch; no frontend code was changed.
