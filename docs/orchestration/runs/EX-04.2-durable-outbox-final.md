## Implementation

- Added `DomainEventOutbox` and additive migration `20261006_durable_domain_event_outbox`.
  UUID primary key is the stable eventId. Versioned envelope, occurrence time, correlation,
  persisted eligibility/hold reason and transport progress are separate fields.
- `CreateOrderUseCase`, `CancelOrderUseCase` and `ProcessPaymentWebhookUseCase` call
  `captureHeld` using their existing EX-03 transaction client. Mandatory insert failure
  propagates and aborts the UOW. Payment captures its state event and, on approval,
  `order.paid` before marking the webhook receipt processed.
- Previously: business tx -> audit -> construct/publish event. Now: business tx includes
  event validation/ID/intent -> commit -> existing audit -> awaited legacy publication
  with the persisted ID. Event occurrence now records capture time inside the transaction.
  Payload/version, public result and audit result shapes are preserved; internal event
  envelopes are excluded from payment result/audit data. Subscriber errors remain awaited.
- Normal records always start `held/pending`, reason
  `legacy_delivery_requires_reconciliation`. No automatic promotion, deletion or cleanup.
  Capture or successful legacy publication never implies delivered/processed/enqueued.
- Bounded claim SQL uses `FOR UPDATE SKIP LOCKED`, DB-clock leases, eligible-only selection
  and attempt counts. Success/defer updates require the current claim token and unexpired
  lease. Transport work runs after the claim statement, outside business transactions.
- `DomainEventOutboxRelay.runIsolatedBatch` validates the stored ID/envelope. Existing
  BullMQ publisher uses `jobId=eventId`; retry codes are safe, capped-backoff metadata.
  A failed post-enqueue DB mark propagates, retaining the claim for lease recovery.
- Relay has **no** Nest registration, timer, controller, scheduler or CLI entrypoint.
  It additionally refuses execution unless both NODE_ENV and APP_ENV equal test.
  In-memory default binding, subscribers and fail-closed worker remain unchanged.
  Eligible rows exist only as explicit synthetic durable-only test fixtures, never
  legacy-published; tests use a unique `ex042-*` queue without a Worker/provider.

## Rollout, rollback and remaining debt

- Schema-first deployment is required: deploying capture code without the additive table
  makes scoped business transactions fail closed. Production deployment is not authorized here.
- Production rollback: revert application capture/DI/relay code together, **retain table
  and all intent records**, then reconcile or forward-fix. Do not run the test-only DROP
  rollback against production or a backlog-bearing DB. Its test targets a new dedicated DB.
- Transport is at-least-once, not exactly-once effects. jobId dedup is queue-scoped and only
  survives while the job exists. Complete Redis loss after `enqueued` has no automated recovery.
- EX-04.3/orchestrator owns handlers, permanent consumer idempotency, single-path cutover
  and historical legacy-effect reconciliation. Flags/restarts must not promote held history.
- Versioned existing payloads contain recipient fields and are now durable in restricted
  DB storage. No public/admin payload endpoint or payload logging was added; protect DB
  access/backups. Retention/reconciliation remains DEBT_DETECTED; no backlog cleanup here.
- Atomicity, real enqueue/recovery, SQL concurrency and reversible migration acceptance
  are PASS in disposable infrastructure. Consumer effect delivery and production activation remain deferred.
