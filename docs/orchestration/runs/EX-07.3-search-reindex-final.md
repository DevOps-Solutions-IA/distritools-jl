## Invariants and implementation

- **PASS (source/unit):** public variants follow existing `ListVariantsUseCase`: variant active and optional parent product active; standalone active variants remain supported. Content follows `PrismaContentRepository.listVisible`: published and inclusive startsAt/endsAt window. Live relation filters protect deactivation, archival and unpublish even when the index is stale. Brand/category checkout sellability rules were not imported into public search.
- **PASS (source/unit):** `PrismaSearchRepository` uses explicit public fields: id, documentType, title, subtitle, sku, brandName/brandSlug, categoryName/categorySlug, placementKey, availability, priority. Internal variantId is selected only to hydrate stock and removed before return. searchText, raw metadata/body, relation IDs, timestamps and index flags are not returned. ORM text predicates remain parameterized; punctuation resembling SQL is treated as text.
- **PASS (source/unit):** q and filters must be strings of at most 256 characters without control characters. Whitespace queries return an empty list. HTTP limits use existing `parsePageSize`: safe positive integers up to 100, defaults 20/10. Missing/structured q and numeric coercions such as `1e2`, hexadecimal, fractions or negative/oversized limits fail with BadRequestException. ID lists use existing UUID validation with a 1000-item cap; omitted/empty lists retain full-reindex behavior.
- **PASS (source/unit):** final identity tie-breaking makes both SQL candidate ordering and ranking deterministic while retaining existing scores. This does not redesign global ranking: candidate selection still uses projected priority/availability before the bounded result cap; autocomplete ordering also uses that snapshot.
- **PASS (source/unit):** reindex eligibility includes current parent status. Inventory uses grouped sums for at most 50 source variants rather than materializing their unbounded inventoryItems relation. Availability is `sum(onHandQty) - sum(reservedQty) - sum(committedQty)`; no clamp, allocation or warehouse eligibility rule was invented. Search repeats this aggregation only for its bounded returned candidates and uses the existing variant priority expression (10 if positive, otherwise 0).
- **PASS (source inspection):** existing batch size 50, UUID ascending cursor, frozen maximum UUID, sorted projection advisory locks and reread after acquiring those locks remain intact. Inbox locks serialize consumerKey+eventId; canonical envelope hash rejects conflicting identity. Projection upserts and inbox progress share each transaction. A failed later batch retains earlier committed cursor/projections and can retry; a duplicate completed event performs no batch work. Delivery budget stays 100 batches, then throws with recoverable cursor. Manual full reindex has a frozen finite upper bound and committed batches; failures are idempotently restartable, with no durable manual operation cursor added.
- **PASS (source/unit):** manual reindex retains JWT guard and `search.reindex`, additionally checking permission at its controller operation boundary. Requested/completed/failed audits share an operation UUID, record projectionKind, fullCatalog/requestedCount and actual completion count. Initial audit failure prevents projection writes. Completion audit failure rejects the request after replayable batches; projection error records failure and propagates. No raw failure payload/PII is persisted.
- **NOT_TESTED (DB):** source-versus-indexer interleavings, persisted rollback/inbox integrity, concurrency, generated SQL behavior and HTTP guards require real isolated services. A unit transaction double is not proof of PostgreSQL rollback. Existing concurrent-indexer coverage rereads after waiting for projection locks; there is no claim that source writers acquire those advisory locks.
