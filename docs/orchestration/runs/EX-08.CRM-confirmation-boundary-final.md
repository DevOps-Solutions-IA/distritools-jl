## Defectos reproducidos y comportamiento final

`crmRequest` compara el ID del recurso devuelto con el segmento solicitado decodificado. No exige UUID a recursos existentes; mantiene IDs sintéticos `q1`, `customer-a` y segmentos codificados. PATCH y reveal de cliente conservan sus contratos y métodos reales. Crear cotización comprueba el customerId conocido contra `customer.id`; no intenta comparar email privado con email enmascarado de un cliente nuevo.

Los efectos provienen del productor vigente: precios → quoted, review → in_review, accept → accepted, reject → rejected, cancel → cancelled. Notas conservan el estado actual cuando el componente lo conoce; `expired` es canónico y aceptado. El envío exige quoted + pending_manual_send y conserva el mensaje manual real. Un sentAt histórico no prueba entrega nueva y el backend no lo borra: no se impone esa restricción. La conversión exige converted_to_order + manual_order_creation_required sin pedido, o la rama backend alreadyConverted:true con pedido existente de forma válida. No se añaden reglas comerciales, stock, checkout, precios, proveedores ni migraciones.

Crear cotización exige un ID nuevo con formato UUID conforme al productor uuidv7 (sin exigir versión7 a fixtures válidas), y las líneas retornadas deben corresponder a producto y cantidad explícitos del request, incluyendo su cardinalidad. La comparación es multiconjunto: no inventa orden de relación ni reutiliza una línea duplicada para confirmar dos productos distintos. No añade redondeo ni reglas de dinero.

`crmRead` conserva la validación de forma y comprueba el ID exacto en rutas de detalle. Las relaciones paginadas mantienen su contrato sin inventar un parent ID. Ante contrato inconsistente las mutaciones retornan contract_error e incertidumbre visible, sin refresh/push, éxito auditado o PII del recurso incorrecto.
