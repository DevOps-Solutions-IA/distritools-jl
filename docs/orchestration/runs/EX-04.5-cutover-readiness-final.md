## Modelo e invariantes de routing

Se agregó `DomainEventRoutingDecision`, vinculado por `eventId` estable al outbox. La decisión, el intent y la mutación de negocio correspondiente se escriben en la misma transacción Prisma. La fila de routing tiene PK por `eventId`, FK `ON DELETE RESTRICT`, checks para route/reason/policy version y trigger que rechaza UPDATE/DELETE. No se retroescribe routing histórico.

Rutas: `legacy_hold` y `durable`. El comportamiento normal, incluido producción, es `legacy_hold`. `durable` sólo se selecciona cuando `APP_ENV=test`, `NODE_ENV=test` y `EX045_TEST_DURABLE_ROUTING=true`, y sólo si el contrato declara producer/consumers seguros y el registry contiene todos los consumer keys estables. Los cinco contratos que declaran explícitamente cero consumers reciben `NOT_APPLICABLE`, pero no se vuelven cutover-eligible por ello.

El outbox relay sólo reclama filas `eligible` con routing persistido `durable`. La publicación legacy usa la ruta persistida; `durable` suprime el publisher legacy. Un error de enqueue deja el mismo durable intent recuperable y nunca hace fallback legacy. Los retries/reconstruction conservan `eventId`. Redis/BullMQ continúa siendo transporte, no evidencia de consumer completion. La semántica sigue siendo **AT-LEAST-ONCE**, no exactly-once.

Se migraron los producers existentes de órdenes/checkout, pagos/webhooks, productos/variantes, marcas, categorías, contenido, promociones y auto-shipping para capturar el evento y routing en sus transacciones correspondientes. Para auto-shipping, quote, selección, guía y fallo escriben `Shipment`/`ShipmentEvent` y outbox/routing juntos; sólo publican post-commit la decisión persistida.

## Cutover, restart, rollback y held history

La simulación aislada cubre:

- default legacy: outbox + `legacy_hold` persistidos; legacy publication contada una vez; relay durable no reclama;
- durable test-only: outbox/routing persistidos; legacy suprimido; relay conserva stable `eventId`; `DomainEventInbox.runOnce` deduplica el efecto lógico;
- reconstrucción con nuevos publisher/repository tras flips: evento legacy sigue legacy, evento durable sigue durable aunque el default vuelva a legacy;
- rollback sólo cambia eventos posteriores; durable enqueue failure deja el evento durable/pending y no invoca legacy;
- job perdido: receipts completados impiden reconstrucción innecesaria; consumer pendiente reconstruye con el ID original;
- parking/retries/notification sent/uncertain guards, Redis outage/recreation, stale leases, worker shutdown y retry budget permanecen cubiertos por EX-04.4.

El histórico held se clasifica read-only. Un snapshot serializado de outbox/routing/parking se compara byte-for-byte alrededor de config flip, evaluator, subprocess bootstrap y simulación. No hay UPDATE de eligibility, routing rewrite, promotion, receipt seeding, bulk replay, borrado ni regeneración de `eventId`.

## GitHub CI portability correction

The first PR CI run exposed that GitHub's generic Redis service starts with appendonly=no, while the EX-04.5 acceptance test intentionally requires the future dedicated queue-Redis contract: appendonly=yes, appendfsync=always, maxmemory-policy=noeviction. The CI job now configures only its isolated Redis service to that contract before the critical suite and verifies the applied values. No production/shared Redis is modified, no product code changed, and no assertion was removed or weakened.

## Mixed-version deployment fence

The pre-merge review found a P2: an EX-04.4 relay understands eligibility=eligible but not the EX-04.5 routing table, so a mixed-version fleet needed a database-visible compatibility fence. EX-04.5 now persists every newly selected durable route as eligibility=cutover_pending. The additive migration extends the outbox constraint to that value. Current EX-04.5 code understands both historical eligible rows and new cutover_pending rows, while the EX-04.4 claim predicate cannot see cutover_pending. A regression proves an EX-04.4-style eligibility predicate has zero visibility into a new durable intent. The cutover evaluator reports MIXED_VERSION_FENCE_NOT_ACTIVATED, and no row is declared cutover-eligible while the fence remains pending. A future controlled activation may occur only after old binaries are proven absent; this phase does not perform that activation.
