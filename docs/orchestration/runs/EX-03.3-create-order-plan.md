## Objective
Remove direct `PrismaService` transaction ownership from `CreateOrderUseCase` behind a narrow order-creation unit-of-work/transaction runner, preserving all current business behavior.

## Current boundary
`CreateOrderUseCase` currently calculates catalog/promotions/totals before the transaction, then opens one Prisma transaction that:
1. reserves stock via `ReserveStockUseCase`
2. creates the order
3. creates order items
4. commits all three atomically

Audit and `order.created` publication remain after commit.

## Invariants to preserve
1. Variant completeness/sellability validation remains before persistence.
2. Promotion evaluation and all price/tax/discount/shipping/grand-total calculations remain unchanged.
3. Reserve-stock + order create + item create remain one transaction.
4. Any failure inside that transaction rolls back stock reservation, order and items.
5. Order number/tracking-code generation semantics remain unchanged.
6. Order status remains `pending_payment`.
7. Customer normalization and snapshots remain unchanged.
8. Audit and `order.created` publication remain post-commit.
9. No event/outbox behavior is redesigned here.
10. No real provider call.

## Allowed implementation
- Add a narrow application port/token such as `CREATE_ORDER_UNIT_OF_WORK`.
- Add a Prisma infrastructure adapter that owns `$transaction`.
- Bind it in OrdersModule or the appropriate existing module.
- Change `CreateOrderUseCase` to inject/use the port instead of `PrismaService`.
- Add focused unit tests for one delegation, one transaction context, result propagation and error propagation.
- Preserve any existing transaction options exactly; if there are no explicit options, do not invent any.
- Reuse the existing transaction-client type if needed to keep scope bounded.

## Hard stops
- No Prisma schema/migration.
- No pricing/tax/promotion/order/inventory rule change.
- No API/DTO response change.
- No retry behavior or transaction isolation change.
- No event/outbox changes.
- No provider credentials/calls.
- No broad transaction-type relocation.
- No weakening/skipping stock contention, rollback, checkout, payment, or critical tests.
- Stop if preserving atomicity requires any of the above.
