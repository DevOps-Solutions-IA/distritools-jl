# EX-04.2 — Durable Transactional Outbox

Status: **PASS / MERGED** via [PR #26](https://github.com/DevOps-Solutions-IA/distritools-jl/pull/26), product merge `a7eb83885b55d93fc2f44821d737d0f61b20d324`. The instructions below are the completed acceptance contract. Evidence: [final record](EX-04.2-durable-outbox-final.md). Next: [EX-04.3](EX-04.3-consumer-idempotency-plan.md).

## Objective
Add a durable outbox for critical domain events so a committed order/payment mutation cannot lose its event intent if the process or Redis fails after commit.

## Scope
Start only with the highest-risk existing flows:
- order.created
- order.cancelled
- payment.approved / payment.rejected / payment.expired
- order.paid when emitted today

Persist event intent in the same Prisma transaction as the business mutation. Relay later with the same stable eventId.

## Required design
- Prisma outbox model + reversible migration
- stable eventId generated once at transaction time
- outbox repository/port
- bounded relay/claim loop with safe concurrency
- enqueue using stable jobId/eventId
- relay crash between enqueue and mark-dispatched must be safe to retry
- no provider calls
- no production DOMAIN_EVENT_PUBLISHER switch unless explicitly required by this runbook; prefer introducing outbox persistence/relay while preserving current contracts
- do not claim exactly-once external delivery; design for at-least-once transport + idempotent consumers later

## Orchestrator decision — relay/worker rollout (2026-10-06)

The relay/worker decision is resolved. Implement EX-04.2 now; do not implement or activate EX-04.3.

### Runtime policy
- Every existing in-scope event-producing business transition must persist its event intent in the same transaction, using that transaction's client. Capture is mandatory; a feature flag must not bypass it.
- Preserve the current in-memory runtime binding, subscribers, awaited publication/audit ordering and request semantics. Pass the persisted eventId to the existing post-commit publication; never generate a second ID there.
- Normal runtime records are capture-only/held for reconciliation. Persist their relay eligibility at creation, separately from transport progress; they must not be automatically claimable. Keep them visible and retained, including when legacy publication fails.
- Implement the BullMQ relay, but leave all normal runtime dispatch entry points disabled. Do not send this outbox's jobs to the current unprepared domain-events worker.
- Use a separate isolated test database and Redis/queue namespace to exercise eligible records and the real BullMQ enqueue path. No production worker or business provider is needed for transport validation. Any isolated durable-only test path must not also publish the same event through legacy subscribers.
- Preserve the EX-04.1 worker's missing/unsupported-handler failures. No no-op handlers, successful discard/ACK, caught-and-hidden failures, domain handlers, generic inbox, or consumer-idempotency implementation in this sub-run.

### Held records and future cutover
Legacy subscribers already have side effects (including notification creation/enqueue). A new inbox in EX-04.3 cannot by itself prove which historical legacy effects ran.

Therefore held records are durable evidence awaiting reconciliation, not delivered/processed records. A relay toggle, restart or future default change must not promote them automatically. Do not delete them, mark them successful because capture/legacy publish succeeded, or replay them wholesale. EX-04.3 must explicitly define consumer readiness, idempotency and a cutover/reconciliation policy before making historical records eligible. New durable routing must select one delivery path for each event.

Keep the mechanism minimal: a persisted eligibility/routing marker plus existing-style transport state is sufficient. Do not build a replay dashboard, generalized routing framework, or a production activation path in EX-04.2. Document a read-only query for held count, oldest age and hold reason.

### Relay guarantees
- Claim a bounded batch atomically. Recover abandoned claims with an expiring lease (or an equivalent proven mechanism), and condition success/failure updates on current claim ownership so a stale relay cannot overwrite a newer claim.
- Do not hold the business transaction open during Redis/network operations.
- Validate the stored envelope and require its persisted eventId; enqueue with jobId equal to that eventId. Preserve the ID across errors, process restart and webhook replay.
- Mark only queue acceptance after successful enqueue; this is not consumer success. Redis errors or ambiguous enqueue outcomes leave recoverable intent and must not be recorded as consumer delivery.
- An enqueue followed by a process crash before marking may enqueue again. BullMQ jobId deduplication is queue-scoped and lasts only while that job exists. This remains at-least-once transport; permanent effect idempotency belongs to EX-04.3.
- No automatic outbox cleanup in this phase. Proving queue acceptance does not establish recovery from complete Redis data loss; record that remaining operational gap accurately.

### Additional acceptance
The original acceptance below remains required. Add:
- normal runtime captures atomically, preserves legacy publication and makes zero outbox relay Queue.add calls;
- held records remain unclaimable after toggles/restart; capture-only records are never reported as processed;
- a failed outbox insert rolls back the business mutation;
- two concurrent relays and an expired/stale claim do not lose events or overwrite valid ownership;
- Redis failure/recovery and crash-after-enqueue retry preserve the same eventId and recoverable state;
- isolated real BullMQ enqueue validation runs without business handlers or provider calls;
- existing missing-handler/unsupported-event tests still fail closed.
