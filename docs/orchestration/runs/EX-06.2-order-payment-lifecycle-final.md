## State and webhook contracts

- Order create starts `pending_payment`; cancellation permits only `pending_payment -> cancelled`; approved webhook writes `pending_payment -> paid`; rejected/expired webhook writes `pending_payment -> cancelled` while payment becomes respectively `rejected`/`expired`.
- Payment statuses in the existing domain are `pending`, `approved`, `rejected`, `expired`, `refunded`. Webhook finalization accepts only a currently pending payment; terminal transitions cannot be re-applied.
- Payment reversal/refund/chargeback transitions are not implemented by this execution. No monetary or accounting semantics were inferred.
- Webhook parser accepts only JSON object payloads with nonblank stable `eventId` and `gatewayReference`, optional string/null `transactionId`, and known `approved|rejected|expired` status. Invalid JSON, missing/ill-typed identity and unknown statuses fail closed; unknown status is not coerced to rejected.
- Controller requires Nest raw-body capture (enabled in `src/app/bootstrap.ts`) and rejects a missing raw body rather than verifying reserialized JSON. There is no verified real provider contract in this phase; only the existing mock HMAC contract is exercised.
- Receipt identity is gateway + stable external event ID. Same identity/same payload returns idempotently; same identity/different payload returns conflict. Distinct concurrent terminal webhook events serialize on the Payment row, with one winner.
- Customer-visible PSE remains unavailable: guest PSE checkout returns conflict before order creation or stock reservation. Existing error/checkout contract is retained; no PSE provider is called and no payment is presented as real.

## Correctness findings and fixes

- Guest PSE was previously able to proceed to order/stock creation despite no configured provider. It now fails before allocation or mutation.
- Guest checkout initially resolved available stock before the idempotency lock, so a stale first lookup could fail after another identical request consumed the last unit. It now re-reads persisted idempotency after the insufficient-stock branch; a deterministic stale-preflight test proves the existing order is returned without additional reservation.
- Order-create idempotency now hashes and canonicalizes request identity, serializes same-key operations with a transaction advisory lock, replays the same persisted order/items and conflicts on changed payload. Legacy callers without a key remain compatible.
- Direct order replay originally returned a newly generated tracking code unrelated to the persisted order number. It now derives the replay tracking code from the stored order number and has an assertion.
- Order/cancellation/payment-intent/webhook audit writes that represent transactional state were moved inside their owning transaction. Fault-injection tests show order, stock, payment, receipt, audit and outbox changes roll back together on injected audit failure.
- Pending payment intents are reused; concurrent creation locks and rechecks the order/payment so only one Payment and one intent event persist.
- Webhook processing now locks and rereads Payment under the lock. Barrier race between distinct approved/rejected events permits one terminal winner, one receipt, and one matching stock terminal movement.
- Duplicate external webhook identity with a different signed payload is rejected instead of being acknowledged as the original event.
- Webhook audit retains only a minimal payment summary and raw payload field consumed by the existing audit redactor. The platform regression verifies the raw payload is `[REDACTED]` and the injected secret probe is not exposed.
- Mock payment initiation now fails closed outside the exact configured local/test environments. Parser and controller reject malformed/unknown outcomes and missing signed raw bytes.

## Fault-injection evidence

- Same-key order duplicate and changed-payload conflict; concurrent same-key order requests; stable order and tracking identity.
- Guest retry with stale idempotency preflight after last available unit is reserved; same order returned, no second reservation.
- Order audit failure and cancellation audit failure leave no partial order/stock/outbox state.
- Pending payment intent duplicate returns same logical intent; deterministic concurrent creation creates one Payment/outbox intent; intent audit failure rolls back both.
- Concurrent approved/rejected webhook events use a barrier and payment row lock; exactly one terminal response/effect is persisted.
- Webhook audit failure rolls back receipt processed state, payment/order transitions and stock movement.
- Duplicate webhook replay and same event ID/different payload; invalid signature; malformed and unknown-status payloads.
- Payment rejection releases reservation and cancels the order; approval commits stock once.
- EX-06.1 inventory operation tests continue proving no negative stock, canonical lock order, multi-line rollback, idempotent reserve/commit/release, and transactional movement/audit behavior.

## Open decisions / limitations

- `BLOCKED_DECISION` — If cancellation wins before a later approved webhook, cancellation releases the reservation and sets order cancelled. The webhook cannot commit absent reservation; its transaction (including receipt insertion) rolls back, leaving the payment pending and the gateway event retryable. Product/Payments/Finance must decide whether this state is held for reconciliation, rejected/cancelled locally, or compensated through an authorized reversal/refund workflow. No option is selected here, no fake paid/refunded state is written, and no provider is called.
- `BLOCKED_DECISION` — `inventory.low_stock_detected` producer remains unimplemented; Product/Inventory Operations owns the authoritative threshold crossing, deduplication, re-arm and payload policy. No threshold or empty producer was invented.
- Provider state remains `BLOCKED_PROVIDER` for real payments/PSE, shipping, email and messaging. Event-bus production relay/worker remains disabled; persisted `legacy_hold`/`cutover_pending` semantics and historical held records are unchanged.
- No chargeback, refund, reversal, successful settlement guarantee, production readiness change, or exactly-once claim. Delivery semantics remain at-least-once.
- Open SEC/GOV obligations from STATE remain open and untouched.
