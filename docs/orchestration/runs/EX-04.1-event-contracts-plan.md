## Goal and bounded architecture

Replace free-form event names and unvalidated payloads with a typed, versioned contract registry; make ownership and consumer dispositions explicit; and make the BullMQ worker dispatch only explicitly registered handlers. A missing/unknown handler or unsupported event version must throw, so BullMQ cannot acknowledge it as successfully processed. Existing in-memory publishing remains the active runtime binding; this phase does not change transport selection, persistence, providers, or business behavior.

The registry describes event contracts and producer/consumer ownership, not a promise that every event is currently consumed. Events without an approved consumer are explicitly marked `not_routed`/`intentional_no_consumer` with an owner and rationale; they must not be given empty no-op handlers merely to make coverage appear complete. Only events explicitly routed to the `domain-events` queue may be expected to have worker handlers.

## Existing baseline relevant to this plan

- `DomainEvent` currently has `eventName: string`, `eventVersion: string`, and generic `payload`; current producers use `v1`.
- Producers publish from order, payment, product, brand, category, variant, promotion, content, and auto-shipping use cases/services; the complete observed inventory and current in-memory consumers are in the discovery matrix.
- Notifications and search subscribe directly to `InMemoryDomainEventPublisher`; no caller of `DomainEventsWorker.registerHandler()` was found.
- `DomainEventsWorker.process()` currently warns and returns when there is no handler, which is an ACK-success path and must be removed.
- `BullMqDomainEventPublisher` uses event name as the queue job name and event ID as job ID; EX-04.1 preserves that envelope and does not bind it as the runtime publisher.

## Proposed contracts and ownership

Define a closed `DomainEventName` union and a versioned payload map for all event names found in the discovery/source inventory. The initial registry must cover at least:

| Event family | Producer owner | Current consumer/disposition to encode |
|---|---|---|
| `order.created`, `order.cancelled` | Orders use cases | Notifications subscriber; queue-side handler only if explicitly routed and wired to the existing use case |
| `checkout.guest_order_created` | Guest checkout use case | No consumer identified; explicit owner decision/disposition, not an empty handler |
| `payment.intent_created` | Payment-intent use case | No consumer identified; explicit owner decision/disposition |
| `payment.approved`, `payment.rejected`, `payment.expired`, `order.paid` | Payment webhook use case | Notifications path; `order.paid` currently resolves no template and must be marked as a known gap, not silently claimed handled |
| `product.created`, `product.updated`, `product.status_changed`, `product.archived` | Product use cases | Search handles first three in-memory; archive has no current consumer |
| `brand.created`, `brand.updated`, `brand.status_changed` | Brand use cases | Search in-memory subscriber |
| `category.created`, `category.updated`, `category.tree_updated` | Category use cases | Search in-memory subscriber |
| `variant.created`, `variant.updated`, `variant.status_changed` | Variant use cases | Search in-memory subscriber |
| `content.published`, `content.unpublished` | Content use cases | Search in-memory subscriber |
| `promotion.activated`, `promotion.deactivated` | Promotion use cases | No consumer identified; explicit disposition |
| `shipment.quote_created`, `shipment.carrier_selected`, `shipment.guide_created`, `shipment.auto_shipping_failed` | Auto-shipping service | Notifications in-memory subscriber; no real provider calls |
| `inventory.low_stock_detected` | No producer found | Notifications subscription exists but is unreachable; encode as producer gap, not a fabricated producer |

Payload interfaces must be transcribed from actual producer call sites, then validated at publish/worker boundaries. Avoid copying recipient PII into logs or adding PII to diagnostic metadata. For each contract, declare its owner, version, current active path, worker-route status, and explicit disposition for absent consumers. Any event name discovered beyond this list must be added with its actual producer owner or rejected pending owner assignment; do not invent producers or consumers.

## Acceptance tests (exact behaviors)

Use the existing `node:test` + `tsx` unit-test convention. Each named test below must assert the stated behavior, not just exercise the code path.

1. `domain-event-contracts.unit.test.ts` — `registry_contains_every_discovered_producer_event`: assert every discovered producer event is registered exactly once with owner, `v1` schema, and consumer disposition; assert `inventory.low_stock_detected` is explicitly producer-missing and no producer is fabricated.
2. Same file — `validates_each_v1_payload_from_real_producer_fixtures`: valid fixtures pass for every registered event; missing required keys, wrong primitive types, and malformed envelope fields fail with a typed contract error.
3. Same file — `rejects_unknown_event_names_and_unsupported_versions`: an unknown name and a known name with an unsupported version fail closed; neither may be coerced to a generic record or downgraded to `v1`.
4. Same file — `ownership_matrix_matches_current_subscribers_and_worker_routes`: assert the notifications/search in-memory subscriptions and their owners match the registry; events with no consumer remain explicitly unhandled/not routed rather than marked consumed.
5. `domain-event-handler-registry.unit.test.ts` — `dispatches_only_registered_handlers`: registered handler is called once with the validated event; unregistered event rejects with a typed missing-handler error.
6. Same file — `duplicate_handler_registration_fails_fast`: registering two handlers for the same event/consumer fails deterministically and does not silently replace the first.
7. `domain-events-worker.unit.test.ts` — `missing_handler_rejects_job_instead_of_acknowledging`: worker `process()` rejects for absent handler; it must not return successfully after logging a warning.
8. Same file — `unknown_event_and_unsupported_version_reject_before_handler`: invalid job envelope rejects and no handler is called.
9. Same file — `registered_handler_success_resolves_and_handler_failure_propagates`: successful handler resolves once; thrown handler error remains rejected for BullMQ retry handling.
10. Same file — `worker_does_not_log_event_payload_or_pii`: captured logs contain only safe event identifiers/name/version and exclude payload, email, phone, address, tokens, and secrets.
11. Publisher contract coverage — `in_memory_binding_remains_default_and_bull_publisher_envelope_is_compatible`: module binding still resolves `DOMAIN_EVENT_PUBLISHER` to `InMemoryDomainEventPublisher`; Bull publisher retains `eventId`, `eventName`, `eventVersion`, `payload`, `occurredAt`, `correlationId`, and stable `jobId` mapping.
12. Focused regression — current notifications and search subscriber tests continue to pass without duplicate subscription or changed in-memory behavior. Run the exact existing focused test files discovered during implementation, plus the new unit files.

## Migration and rollback assumptions

- No database migration or persisted-data backfill is expected because EX-04.1 adds compile-time/runtime envelope contracts only; verify this remains true before implementation.
- Preserve the existing wire envelope and `v1` event names/payloads. Any incompatible payload correction requires a separately versioned contract and explicit producer/consumer rollout order; do not silently reinterpret existing jobs.
- Keep the default publisher binding in-memory and do not enable BullMQ dispatch. Existing queued jobs with unknown names/versions must fail processing rather than be acknowledged; retain the queue's existing retry behavior and do not claim a DLQ/parking policy in this phase.
- Rollback is a source revert of the EX-04.1 code commit. Since no schema/data migration or transport switch is allowed, rollback must not require data restoration. If implementation finds queued-job compatibility or deployment-order risk that invalidates this assumption, hard-stop and seek an orchestrator decision.
