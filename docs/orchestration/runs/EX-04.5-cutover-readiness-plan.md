## Objective

Prove that a future cutover can be deterministic, restart-safe and rollback-safe by adding or proving all of the following:

1. full Nest bootstrap behavior when queue Redis is unavailable before process start;
2. a persisted per-event routing decision for new events so deployment clocks/config changes cannot create dual delivery;
3. complete required-consumer disposition evidence per event contract;
4. read-only cutover and historical classification reports;
5. isolated canary/cutover/rollback simulations with no production activation;
6. compatibility across restart and mixed-version deployment boundaries.

PostgreSQL remains authoritative. BullMQ transport state is not proof of consumer completion or provider delivery. Delivery remains at-least-once.

## Scope

### 1. Full bootstrap with Redis absent

Add an owned subprocess/bootstrap test that starts the actual Nest application role with:
- dedicated disposable PostgreSQL;
- queue Redis unavailable from process start;
- no real providers;
- production-like auth/security fail-closed settings.

Prove:
- process does not hang indefinitely;
- liveness remains bounded and truthful;
- readiness returns degraded/503 within the documented bound;
- producer initialization does not loop forever;
- durable worker remains unavailable unless explicitly authorized;
- shutdown remains bounded even if Redis never became ready.

Do not weaken startup or auth/security policy merely to make this pass.

### 2. Persisted routing boundary

A routing decision for a newly captured event must be persisted with durable event intent. It may be represented by an additive field or dedicated additive routing record, but it must satisfy:

- identity is bound to the original stable eventId;
- route decision is durable across restart;
- changing environment variables or process clocks cannot alter an already-persisted route;
- rolling deployment cannot cause the same event to use legacy and durable paths;
- no automatic fallback to legacy after a durable enqueue failure;
- rollback affects only events captured after the new routing decision;
- old events retain their original route;
- default production behavior remains legacy+held until a separate authorization.

Suggested route concepts may include legacy_hold and durable, but choose the smallest representation compatible with the current schema and migration conventions.

Any schema change must be additive and preserve all existing outbox/inbox/parking/audit history.

### 3. Required-consumer disposition matrix

Derive the required consumer set from existing contracts/discovery and current handler identities. For every current domain event, record one disposition per required consumer:

- SUPPORTED_DURABLE: real registered effect with stable inbox identity;
- BLOCKED_GAP: required effect is known but not safely implementable in this execution;
- NOT_APPLICABLE only when supported by the existing business contract/evidence.

Do not use NOT_APPLICABLE to hide missing work.

Known gaps remain explicit:
- order.paid notification-template/business-template gap;
- inventory.low_stock_detected producer gap;
- any unresolved lifecycle owner/disposition.

Do not invent a template, producer, owner, no-op handler or business effect.

An event cannot be cutover-eligible while any required consumer is unresolved.

### 4. Cutover evaluator and dry-run

Implement or extend a read-only evaluator that reports, without modifying rows:
- event contract/version;
- persisted route;
- required consumers;
- completed receipts;
- pending/recoverable work;
- parked/uncertain work;
- unsupported/missing dispositions;
- eligibility reason;
- held-history classification.

The evaluator must be bounded, paginated and safe for operator use. It must not expose payload/PII/provider responses/secrets.

Dry-run output is evidence only. It must never seed inbox receipts, change routing, promote held rows or enqueue work.

### 5. Isolated cutover simulation

In isolated test services only, prove a sequence equivalent to:

A. default legacy_hold event:
- business transaction commits;
- outbox captures stable ID and legacy_hold route;
- legacy publication happens once;
- durable relay cannot claim it.

B. authorized test-only durable event:
- routing decision is persisted atomically with capture;
- legacy publication is suppressed for that event;
- durable relay/worker processes through the same idempotent consumers;
- same stable eventId survives queue retries/restart;
- all required safe consumers complete once logically.

C. restart/config flip:
- an already-persisted route remains unchanged;
- no dual publication;
- no process-clock transition.

D. rollback:
- route default for future events returns to legacy_hold;
- previously durable-routed events remain durable and recoverable;
- no fallback duplicate through legacy.

This is a test-only simulation. Do not expose a normal production activation switch in this phase.

### 6. Historical held boundary

Historical held records remain a separate class.

Allowed:
- read-only classification;
- counts and safe IDs/categories;
- evidence of per-consumer completion where it already exists.

Forbidden:
- UPDATE of held eligibility;
- bulk replay;
- receipt seeding;
- route rewriting;
- eventId regeneration;
- promotion based on missing Redis/job/inbox evidence;
- assuming projection presence proves all effects.

### 7. Queue Redis deployment contract

Validate, without modifying shared infrastructure, the configuration contract required for a future dedicated queue Redis:
- persistence enabled;
- noeviction;
- isolated from auth/security/cache workloads;
- backup/restore procedure documented;
- health/readiness behavior bounded.

A local/disposable restore drill is allowed. A production infrastructure change is not.

## Acceptance tests

At minimum prove:

1. Full Nest subprocess boot with Redis unavailable before start returns bounded liveness/readiness behavior and shuts down without hanging.
2. Default production-like routing remains legacy_hold.
3. Route choice is persisted atomically with event intent.
4. Restart and environment/config changes do not alter an existing event route.
5. A test-only durable-routed event never also publishes through legacy.
6. Durable enqueue failure does not trigger legacy fallback.
7. Rollback changes only future route decisions.
8. Same eventId is preserved across durable retry/restart/reconstruction.
9. Required-consumer gaps make an event ineligible.
10. Supported consumers still dedupe across legacy/durable invocation boundaries.
11. Parking/uncertain/sent notification guards remain authoritative.
12. Historical held fixtures remain byte-for-byte unchanged.
13. Cutover dry-run is read-only, paginated, bounded and redacted.
14. Redis persistence/noeviction contract can be validated against an owned disposable Redis; restore/job-loss behavior remains recoverable from PostgreSQL.
15. Existing checkout/order/payment/search/notification/admin regressions remain green.
16. No real provider is called and no normal production activation path is introduced.

Use barriers and explicit deadlines. Do not use arbitrary sleeps or retry-until-pass to hide races.
