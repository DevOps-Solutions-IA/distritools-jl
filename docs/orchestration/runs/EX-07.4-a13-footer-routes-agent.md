## Approved decision and implementation

The user's Product/Content/UX reply authorizes actual Next public route authority plus actual backend resolution of dynamic published resources. Syntax alone is insufficient. F3 is not waived, excluded or weakened.

`generate-storefront-route-registry.js` deterministically walks real Next App Router page source files, strips route groups, and excludes admin/API/private folders, parallel slots and intercepted pages. No manually curated destination list is used. The generated TypeScript registry currently has 29 route patterns: 22 static and seven dynamic, including pages implementing actual `/storefront` aliases. A digest includes all public page source bytes/relative paths, actual Next configuration, CatalogToolbar, filtering and mappers; `--check` rejects stale output. A `pageExtensions` override fails closed until its generator semantics are explicitly supported.

`--check-manifest [optional-path]` first checks registry drift, then parses the actual built Next `.next/server/app-paths-manifest.json` and requires exact public route-pattern parity. It rejects missing or incompatible manifests. The default manifest path is relative to the repository, independent of invocation cwd. Fixture parity is evidence for the parser, not a substitute for a real Next build.

`footer-route-authority.ts` exports:

- `FOOTER_LINK_LIMIT = 1000`: shared technical ceiling on total revision links; all groups are counted before catalog queries, with concrete HTTP400 overflow rejection. This bounds input/legacy public projection work and is not a route/stock policy.
- `FooterRouteClient = Pick<Prisma.TransactionClient, 'product' | 'category' | 'brand'>`.
- `inspectFooterHref(client, href): Promise<{ valid: boolean; reason: string }>`.
- `assertFooterRoutes(client, groups: readonly { links: readonly { href: string }[] }[]): Promise<void>`; failures are concrete HTTP400 `BadRequestException` messages with one-based group/link positions.

The authority accepts only literal internal ASCII path segments; it rejects external/protocol-relative schemes, fragments, backslashes, duplicated or trailing slashes, dots/traversal, encoded path segments, controls, whitespace and manipulated paths. Supported catalog query parameters are validated separately as data without normalizing the destination path. The 2048-character parsing ceiling bounds input work and is not a destination whitelist. Static routes must actually exist in the generated registry. Dynamic canonical and legacy product/category/brand pages use `findUnique({ where: { slug }, select: { isActive: true } })`, and require current `isActive === true`, matching existing public catalog visibility. No stock, price, variant, related-brand/category, sellability or ranking policy was added. There is no separate public `isPublished` field on these catalog resources.

CMS/Legal database slugs do not create real App Router pages; invented `/contenido` or `/legal` destinations remain rejected. The real `/storefront/orden/[orderNumber]` pattern is registered as a real page but remains rejected as a footer destination because no approved resource-resolution authority exists for that dynamic family. No order lookup/disclosure was invented. Valid/invalid reason strings are fixed and do not interpolate href, slug, label, PII or database errors. Database exceptions propagate fail-closed rather than approve unvalidated links. Each dynamic call rechecks current visibility; no long-lived positive validation cache exists. Inspection results are fresh objects, so mutation of a caller's prior result cannot alter subsequent decisions.

The generator uses existing TypeScript AST tooling (frontend dependency when installed, otherwise root dependency) to derive query keys from actual catalog/search page reads, static `source`/`destination` aliases from actual Next configuration, and status/sort values from the actual CatalogToolbar options. It emits byte-identical backend/frontend pure readonly `STOREFRONT_ROUTE_QUERY_KEYS` and `STOREFRONT_QUERY_VALUES` metadata with no Node/Nest/Prisma imports for frontend reuse. The approved catalog/search scope supports the actual page contracts: `/productos` brand/category/q/status/sort; `/buscar` q; category detail brand/q/status/sort; brand detail category/q/status/sort; product detail no query. Actual Next aliases inherit destination contracts. Noncatalog transactional confirmation/order parameters have no approved footer resource authority and remain fail-closed. Computed unknown query keys, missing/nonliteral enum source authority and cyclic redirects fail generation rather than invent an allowed set.

URLSearchParams decodes supported query data after explicit percent/UTF8 validation. Duplicate or unknown keys, encoded/obfuscated keys, invalid escapes, decoded controls, unsupported enum values and manipulated resource slugs are rejected before database reads. Safe percent-encoded UTF8 q is search data, including a slash in search text, never a redirect destination. The existing 2048-character href ceiling also bounds query work; no arbitrary new search/ranking rule is added. Empty form filter values retain their real no-filter/default semantics. Nonempty brand/category filters require actual currently active resources, and are revalidated after depublication; each link performs at most three bounded resource reads (destination plus two filters).

Save/review/publication transactions and post-publication storefront hiding/durable alerts depend on A14/A15. This module alone does not implement those workflows or satisfy persisted F3.
